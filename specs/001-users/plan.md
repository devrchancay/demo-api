# Plan

Five routes on the existing Fastify app, following the layering the template already uses
for `/health`: the logic in a service, the HTTP shape in a route file, and `app.ts` only
wiring them together.

The store is a `Map` held inside the service module. No database in this iteration, which is
what lets the tests run inside a sandbox with no Postgres — the same reason `/health` reports
`not-configured` when `DATABASE_URL` is absent.

Ids are generated by the service with `crypto.randomUUID()`, so nothing new enters the
dependency list and the caller cannot choose an id.

## Inventory components

- fastify@5
- zod@3
- vitest

## Data

None on disk. In memory the service keeps `Map<string, User>` where a `User` is
`{ id, name, email, createdAt, updatedAt }`. The email uniqueness check is a scan of that
map, which is fine at this size and is a unique index once the table exists.

Replacing the map with a table is a later spec, and that is when `pg@8` enters the components
list. Keeping the service as the only module that touches the store is what makes that swap
a change in one file.

## Shape of the routes

| Route | Answers |
|---|---|
| `POST /users` | 201 with the user · 400 invalid body · 409 email taken |
| `GET /users` | 200 with the list, empty when there are none |
| `GET /users/:id` | 200 with the user · 404 unknown id |
| `PATCH /users/:id` | 200 with the user · 400 invalid body · 404 unknown id · 409 email taken |
| `DELETE /users/:id` | 204 no body · 404 unknown id |

## Validation

One zod schema per body: the create schema requires `name` (non-empty) and `email`
(`z.string().email()`); the patch schema makes both optional but rejects an empty object, so
`PATCH` with nothing to change is a 400 rather than a silent no-op.
